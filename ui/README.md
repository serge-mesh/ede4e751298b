# Picket web UI

The web UI of picket-core (core.md §12): React, TypeScript, Vite, Tailwind CSS, shadcn/ui
(Radix), TanStack Query / Router / Table, Recharts, CodeMirror 6, with a client generated by
`openapi-typescript` and `openapi-fetch`. `npm run build` writes `ui/dist`, which picket-core
embeds with rust-embed (debug builds read it from disk).

## Commands

Use Node ≥ 26.13.1 (the exact version in the repository’s `.node-version` in CI).

The `typescript-native` alias supplies the TypeScript 7 compiler used by the build and lint
scripts. `typescript` stays on 5.9.3 for the compiler API required by ESLint and
`openapi-typescript`; invoke the compiler through the npm scripts to select it explicitly.

```sh
export PATH=$HOME/.local/opt/node/bin:$PATH
npm ci            # install the pinned dependencies (package-lock.json)
npm run lint      # eslint (no warnings allowed) and tsc
npm run build     # type-check and build ui/dist
npm test          # vitest: API client, schema forms, every page and the main flows
npm run dev       # dev server; proxies /api, /lists, /lanca to PICKET_CORE_DEV_URL
```

`PICKET_CORE_DEV_URL` defaults to `https://127.0.0.1:8443`; a test instance runs as an ordinary
user with `picket-core init --data-dir <dir> --web-port 18443 --edge-port 17443` and
`picket-core run --data-dir <dir>` (the first admin password is in `<dir>/initial-password`).

## The API types

`src/api/openapi.json` is core's OpenAPI document (`/api/ui/v1/openapi.json`) and
`src/api/schema.d.ts` the types generated from it. Regenerate both after a core API change:

```sh
ui/scripts/update-openapi.sh                    # builds picket-core, runs a throwaway instance
ui/scripts/update-openapi.sh path/to/picket-core  # or use an existing binary
PICKET_CORE_URL=https://host:8443 PICKET_CORE_PASSWORD=… ui/scripts/update-openapi.sh
```

Entity forms are rendered from the bundled document's component schemas, so a new field in core
shows up in the UI after this step without UI code.

## Rules the code keeps

- Text from outside core is React text only; control, bidi and zero-width characters are shown
  escaped (`SafeText`, `lib/text.ts`). ESLint forbids `dangerouslySetInnerHTML`, `innerHTML`
  and `eval`.
- Every mutating request carries `X-Picket-UI: 1` and a JSON body (`api/http.ts`).
- No inline scripts, no `data:` assets other than images: the build works under core's CSP.
- Endpoints and chart series core doesn't serve yet are listed in one registry,
  `src/api/availability.ts`. Only those show "not available yet" while core answers `404` (no such
  endpoint) or `422 unknown series`; the same answer for anything else is an error, so a typo in a
  path or series shows. Core's `501` is always "not available yet". A chart leaves out a registered
  series core doesn't record yet and names it below the chart. Core 826b4d6 (wave 5) serves every
  endpoint and records every series the screens use, so the registry is empty; add an entry when a
  screen is built ahead of core again.
- Every series core records or receives is charted or listed on a page: core's OpenAPI document
  lists them (`MetricSeries`, from its series registry), and `src/pages/metrics-coverage.test.tsx`
  renders the metrics pages against a mock core that answers every series with data and fails on
  a series none of them draws (or lists it as an exception, with why). Charts, tables and figures
  name the series they draw in `data-rendered` (a derived line, such as `fw.entries ÷ fw.max`,
  names its sources). A core unit test keeps `src/api/openapi.json`'s catalog current.
- Wave-5 screens read core's real shapes through the generated client: the query log (attribution
  `state` with roles and `by`, the `response` reply, the upstream `answer`, lookups with their
  `detail` object shown as JSON text as an alert's, trial would-blocks, the checks), `top`, devices (`ptr`/`dhcp_name` are null: core learns no PTR or DHCP
  names), the device and profile views, trial results with core's own `limits`, alert evidence
  (copies, counts with their "other" rows, answers, `wire_mismatch` examples; **Download as fuzz
  case**, an answer's or reply's wire and the whole evidence download as files), lookup modules and
  presets, a provider's status, Test now (core answers with the self-test's result; its `409`
  "provider is being reloaded", while core's lookups haven't loaded the last save, shows under
  the actions with Retry) and flush,
  temporary allows (paged per state: `active`, `recent`; `revoked` is its own state: the edge
  acknowledged the revoke and its end isn't logged yet), the DNSSEC queue and results (paged,
  Bogus by default) and the extension builds. Devices show the MACs core currently knows (`macs`,
  core 07acc1c: nothing inferred): a device's own (`mac`: its key, or for a device keyed by a
  client name the first MAC of the client entry with that name now) with the private-MAC and
  Hyper-V marks, none for a client name no entry has now or whose entry lists none, and an
  address-keyed device's (`mac` null) as "seen at its address", since it may be another device's;
  **Add as client** takes the device's own MAC, else its addresses, never a MAC seen at its
  address, and offers a device keyed by a former client's name under that name. The device and
  profile views list their allows with their state, as of each edge's last report (core's summary
  has no `revoke_pending`: Temporary allows shows a pending revoke); the trial graph follows the
  edge selector (core 720be97 counts would-blocks per edge). An alert raised from records of
  several edges (`edge` null where its kind's details show the records had an edge:
  `category_blocked`, `category_answered`, `dnssec_bogus`, `upstream_disagrees`) says "several
  edges"; a `category_blocked` alert lists what blocked the query: its feeds (`details.feeds`) or its sync lookup providers (`details.providers`:
  category, score, reason, verdict cached or fresh, detail).
- Alert evidence is paged with core's cursor, newest stored first (core c58ba80: the order core
  stored the copies, not their event times; 100 copies a page, **Load older copies**, core's
  `total` as the last page read gives it); when every older copy is loaded and core counts more,
  they were stored after the first page was read, and **Show the newest** reads the pages again
  from a fresh first page. The counts, examples and rule come with the first page; **Download
  evidence** reads every page (500 a request) and saves them joined; a read that copies came in
  during (totals or count differ, or the newest copy changed by the end) is made again, up to 3
  times, then saved with a warning. An open copy stays open by its record (edge, boot, seq) as
  newer copies shift the rows. It's read again only when an `alert` event lists its alert (not
  deleted; core 4e4f53d lists it for new evidence too) or lists only some (`alerts_truncated`), at
  most every 30 s, the loaded pages in order.
- Live events (core's `UiEventFrame`): `alert` (coalesced since core a3eb6d5: the alerts changed
  since the previous one, at most 64 listed) re-reads the alert views and the lists alerts change
  once per event; `feed_run` (coalesced too: the runs stored, at most 64 listed) the feed
  statuses, the provider views, every feed's status, checks and schedule (a check changes them
  without storing a run) and each listed run's feed's runs and entries, and places the run for
  its feed (a closed editor's cached file marked stale by a later save, an open editor's save
  result); when the event lists only some (`runs_truncated`), every feed's views, every closed
  editor's file stale, and an open editor reads its runs;
  `temp_allow` re-reads the allows lists of the edges it names and the device and profile views; `dnssec` the queue and the results lists of the
  outcomes it counts (or every outcome's), the newest page alone past one page, at most one read
  every 2 s (`refreshPagedLists`: stored results never change); `dnssec_queued` (every other
  change to the queue: checks queued, joined, retried, waiting, ended, dropped, stamped) the DNSSEC
  queue;
  `lanca` (a root `rotated` or a previous one `previous_dropped`, naming the `previous` root) the
  settings and the identity; `lanca_served` (an edge's listeners moved to the current root) the
  settings; `restore` everything, in every tab (as a reconnect or `lagged` does), once per restore
  `generation` in the tab that restored (its answer carries it too, core 07acc1c), dropping
  closed editors' cached files and resetting an open editor from a file read (a restored file
  keeps the export's save time); in the tab whose answer came first, `feed_run` events before the
  restore's own event (core sends them ahead of it) aren't placed; an
  `edge_status` `hello` or `session_ended` from an edge keeping a previous LAN CA root in use
  re-reads the settings (its online state; heartbeats don't). Temporary allows, DNSSEC results
  and the DNSSEC queue poll (60 s) only while the event socket is down, and with a bundle's build
  status and core's identity read once more when it first opens (`READ_ON_OPEN`: a read answered
  before core subscribed the socket can miss an event). Each time the socket opens, core's
  identity `version` is compared with the one the page loaded with; when they differ, a banner
  offers Reload (never automatic: drafts could be lost).
- Paged lists (query log, temporary allows, DNSSEC results) keep their rows on an error: a failed
  refresh shows above them, a failed "Load more" below, with Retry for that page. Polling and the
  focus refetch read the loaded page while one is loaded; past that (a refetch would read every
  loaded page again), they read the first page alone and join it to the loaded ones, so new rows
  show and older pages stay (`usePagedList`, `withHead` in `api/queries.ts`).
- Settings → LAN CA shows the current root (fingerprint, zones, when it was made, DER and PEM),
  the previous roots core still trusts with the edges whose managed listeners haven't reported a
  certificate from the current root (each edge online or offline), and the zones, editable: a
  change is a new root, confirmed after a warning (trusted again on every device; edges re-issue
  their certificates by themselves; the old root stays until every edge reports the new one), sent
  as `{lanca: {zones, rotate_from}}`, `rotate_from` the root the draft was edited against (core
  c58ba80 rotates only with it). A dirty draft whose root another change replaced says so (naming
  the root it replaced, from core's `lanca` event) and offers Reload or Keep my zones; a clean one
  follows. The done alert names the root replaced, and `previous_dropped` says the rotation
  finished, naming the root dropped. No change is offered while a previous root is in use or
  core's clock isn't synchronised (`clock_synced`, said why; the tab reads the settings every 30 s
  until it is, as core sends no event). Core's `409`s show by their code (core 07acc1c):
  `lanca_root_changed` (a root replaced meanwhile: the root core has now, and **Reload settings**
  puts the draft on it to decide again) and `conflict` (a previous root still in use: wait, and
  the refusal says so once settings read after it give `can_rotate`); `503 unavailable` (the
  clock) and `422` (names to move first, with the two-step path; zones core won't take) show in
  words. An answer lost after core may have committed (no answer, any other
  5xx) is judged by the settings read again: a new root for the zones shows as done, the same
  root as not known yet (a later new root for the zones shows as done), none readable says how
  this browser gets the new root; a `200` naming the same root says nothing changed. The warning
  and the done alert say devices fail as soon as their edge re-issues, and, with `web.tls`
  managed, that this browser loses the page on its next connection (install the root now, or get
  it over `web.http_port`). No other settings form sends the zones, and "Keep my changes" never
  merges them.
- Config export and restore: one export and one restore at a time (`409`), a document of at most
  1 GiB (`413`; a larger file is refused before it is sent), room on the data disk (`507`), and
  core's `422` (a part too large to export, a malformed document, other `lanca.zones`: change them
  under LAN CA first, a bad reference with its issues, a newer format) shown in words; a restore
  lists the secrets still missing a value and core's warnings (a committed restore is always a
  `200`, its edges' configs that couldn't be rendered yet among the warnings), and everything cached is read
  again, reads still in flight replaced (on core's answer or its `restore` event, whichever comes
  first: both carry the restore's `generation`; reconnects and `lagged` do the same). Before sending, the document's top level is read in chunks for `format_version`
  in any key order (up to 64 MiB; past that, or when it's cut short, the page warns and core
  checks); a feed export, a non-object or a top level without `format_version` is turned away.
  The export shows its progress against core's `Content-Length` and Cancel ends it (core frees its
  export slot); it's held in memory until saved, so very large exports are best downloaded on a
  desktop browser. Manual files travel as base64 chunk lists.
- Edit forms compare live data with the value they were edited from: a clean form follows new
  data, a dirty one keeps its draft and offers Reload or Keep my changes (`lib/merge.ts`; fields
  core checks together, such as a profile's `block` and `trial_bundles`, merge as one value).
  Every write to an entity runs in one queue per entity (`serialised` in `api/queries.ts`):
  read-modify-write actions (Add to bundle…, Enforce, Disable, …) read the entity fresh in their
  turn, and a form save is sent only while the entity still equals the form's base.
- A manual feed's file is never in React state or refetched by events: the editor keeps it in
  CodeMirror, its base is the save its last save returned (version and `saved_at`), and imports
  and restores are read from the chosen `File` and sent as a `Blob` built once from bounded parts
  (`lib/import-file.ts`). An import core couldn't take is refused before the file is read: a
  JSON export up to 32 times the download size cap, anything else (sent as `{"file": …}`) up to
  the cap itself, read from the settings (core's default, 256 MiB, when they can't be read).
  Saves are placed by core's save time alone (`pages/manual-line.ts`): every write returns it, a
  run carries it as `updated_at`, a `feed_run` event as `saved_at`; versions are content hashes
  and repeat. A page write that ends without a save to wait for (failed, unchanged) has open
  editors read the runs again. The feed's status gives the file's version without its content
  (an import's `base_version`) and `manual_retry_at` (a run is coming, or none is).
- Views that show heavy jobs follow `job` events (System, Build now, a manual save's run) and
  poll only as a fallback: while the event socket is down, or for what no event covers (a
  provider check, the light lane). A report can be missed (a reconnect, `lagged`, a `job`
  event's `dropped`), and those re-read the statuses: a held report of a running job ends once a
  status read sent after it arrived says the job isn't running (`api/order.ts` orders reports and
  reads). Build now follows its build from the click, so events that come before the request's
  answer count, and a status read after the answer that shows no build ends it.
- Import… sends feed settings only for a file that declares none (core refuses, `422` naming the
  field, one that differs from an export's) and shows core's issues in the dialog.
- Every `limit` the UI sends is a constant inside core's bounds (core 07acc1c refuses one outside
  with 400: 1 to 500, 1 to 100 on `top`). A feed provider's Backtest takes Days (1 to 60, default
  7) and k (0.1 to 50; blank for each of 1, 2, 3 and 5), bounded by core's document
  (`queryRange` in `lib/openapi.ts`): a value outside is refused in the form, with the range, and
  nothing is sent.
- Device views link `/clients/device?key=…`; core serves the UI document for dotted paths too, so
  `/clients/device/192.168.1.20` works as well.

## Tests

Every request a test makes is checked against core's OpenAPI document and the rules core adds
(ids it refuses, the enums its query types take, an import's settings against an export's or the
feed's): `src/test/contract.ts`. A mock route that answers 2xx to a request core would refuse
fails the test; a route that answers 4xx, or says it `refuses` (it answers core's `422` itself),
isn't checked. Query values are checked against the document's parameter schemas (core 720be97
types them: enums, whole numbers, required ones; core 07acc1c bounds them: every `limit` 1 to 500,
1 to 100 on `top`, the backtest's `days` 1 to 60 and `k` 0.1 to 50, else 400). The rules beyond
the document are modelled too: the refusals of `logs`, `top`, `query-summary`, `trial-results`,
`temp-allows`, `dnssec/*` and the evidence's cursor (400s, among them a cursor core didn't give,
and 422 for a window past the query-log retention; the evidence's cursor is core c58ba80's, a
copy's row id), the preset body limit, PUT `settings`' `lanca.zones` (in core's order: `422` for
zones core won't take, without `lanca.rotate_from` (or with null) or for orphaned names, `409
lanca_root_changed` for a replaced root, `409 conflict` for a previous root in use, `503` while
the clock isn't synchronised) and a restore's format (0 and newer ones refused) and zones. For PUT
`settings`, Test now and the evidence, a mock's error answers are checked too: a status or error
code core's handler doesn't give there, or not for this request (a `409` whose code the state
decides), fails the test. So do a restore's answer without its `generation`, and a `lanca`,
`lanca_served`, `dnssec_queued`, `restore`, `job`, `alert` or `feed_run` frame a test emits in a
shape core doesn't send, or a coalesced list core wouldn't fill so (64 listed when truncated, every
change listed otherwise: `src/test/events.ts` builds these frames and `job`'s). A GET route
marked `pure` (its body function only reads the test's state) answers the rules that need core's
state, such as the current LAN CA root. Core's manual feed (content-hash versions, save times in writes, runs and `feed_run`
events, 409s, the run row written when a run ends, `status.busy`, `manual_retry_at`, imports) is
mocked in `src/test/manual-core.ts`; other stateful mocks live with their tests.

Fixtures are captured from real cores: `src/test/fixtures/core.json` (its `/settings` carries the
LAN CA view in core c58ba80's shape), and the wave-5 answers in `src/test/fixtures/w5.json`
(`src/test/core-w5.ts`), captured from core a3eb6d5 with data by `scripts/capture-w5.mjs` (manual
feeds, a block and a trial bundle, a profile, clients, a disabled feed provider, a lookup provider
and a block by it, records posted through the edge API by two fake edges, devices keyed by a
former client's name and by the name of an entry without MACs, a session acknowledging a revoke
and reporting its listener's root, a LAN CA rotation with core's refusals, every kind of `limit`
and the backtest's `days` and `k` out of range, a second core whose clock isn't synchronised,
and the UI events core sent meanwhile, among them a burst of alerts raised and bulk-deleted whose
`alert` events list only some). The mock core answers GETs from
both when a test gives no route of its own. Tests of the "not available yet" mechanism register
endpoints and series for themselves (`src/test/registry.ts`).
