# CI security

## Code scanning

CodeQL runs as two jobs in `.github/workflows/ci.yml`, `CodeQL (rust)` and `CodeQL
(javascript-typescript)`, with the `security-extended` queries
(`.github/codeql/codeql-config.yml`). They run on pushes to `main` for the languages the push
changed (Rust sources, manifests, the lockfile and the toolchain select Rust; JS/TS sources, npm
manifests and lockfiles, and `.node-version` select JavaScript/TypeScript; the CodeQL config and
`ci.yml` select both), and weekly and on manual runs for both. They don't run on PRs: across the
first PR scans, none found anything the scan of `main` hadn't. The `fuzz/` workspaces are
excluded: they are test harnesses, and loading their eight Cargo manifests took minutes of every
Rust scan. A third job, `CodeQL (rust, fuzz workspaces)`, scans them monthly under its own category
(`/language:rust/fuzz`), reporting only alerts in `fuzz/` (`.github/codeql/codeql-fuzz-config.yml`)
so the crates they call aren't reported twice. A manual run of `ci.yml` can pick `codeql` or
`codeql-fuzz` to scan on demand. Results appear under **Security → Code scanning**.

GitHub Actions workflows are checked by zizmor (`.github/zizmor.yml`) in the first CI job
whenever a workflow, `dependabot.yml` or the zizmor config changes, and in weekly and manual runs;
it replaces CodeQL's Actions analysis. Its findings fail the job and appear as annotations.

Both languages use `build-mode: none`: analysis does not require installing application
dependencies or executing project build scripts. Rust code generated by build scripts may
therefore be absent from the scan. The Rust build, clippy and test jobs still run in `ci.yml`,
along with `cargo deny` for RustSec advisories, licenses, bans and sources, and
`.github/workflows/rustsec-advisories.yml` checks advisories daily for the root and every fuzz
lockfile.

Only the SARIF-uploading jobs (the CodeQL jobs and `sonar-sarif.yml` `sync`) receive
`security-events: write`, and only the daily advisories job receives `issues: write` (to report a
failure); every other job has `contents: read`. Unselected jobs skip before allocating a runner.
Workflows use `pull_request`, which needs no repository secrets for Dependabot and fork PRs.
Actions are pinned to commit SHAs, checkout does not retain Git credentials, and Dependabot
maintains those pins. Tool binaries (cargo-deny, cargo-zigbuild, cargo-nextest, typos, zizmor)
are downloaded at pinned versions and checked against pinned SHA-256 sums
(`scripts/install-ci-tool.sh`).

## SonarQube Cloud SARIF sync

SonarQube Cloud analyzes the repository automatically via the SonarQubeCloud GitHub App, but
its native GitHub Code Scanning integration requires the SonarQube Cloud Enterprise plan.
`.github/workflows/sonar-sarif.yml` bridges open SonarQube Cloud findings (Vulnerabilities,
Bugs, and Code Smells) into **Security → Code scanning** under the `SonarQube Cloud` tool
(`category: sonarqube-cloud`):

- Triggers when a `sonarqubecloud` check run completes (on `main` or a pull request), on a
  daily schedule (so issues accepted or resolved in SonarQube Cloud propagate without a new
  commit), and on manual `workflow_dispatch`.
- Runs `scripts/sonarcloud-to-sarif.py` from the default branch without checking out or
  executing pull request code. For this public project, it queries SonarQube Cloud's public
  API without requiring a secret; if the repository is ever made private, set a `SONAR_TOKEN`
  repository secret (and optionally a `SONAR_PROJECT_KEY` variable if the key differs from
  `<owner>_<repo>`).
- Maps Sonar `VULNERABILITY` findings to GitHub `security-severity` levels (Critical, High,
  Medium, Low) and `BUG` / `CODE_SMELL` findings to SARIF `error` / `warning` / `note` levels,
  with direct links back to each SonarQube Cloud issue.
- Synchronization is one-way (SonarQube Cloud → GitHub): resolving or accepting an issue in
  SonarQube Cloud closes the corresponding GitHub alert on the next sync, whereas dismissing
  an alert in GitHub does not update SonarQube Cloud. Security Hotspots remain in SonarQube
  Cloud.

## Dependency updates and review

`.github/dependabot.yml` checks weekly (Mondays) for version updates to:

- GitHub Actions in `.github/workflows`.
- The root Cargo workspace and all independent `fuzz/*` workspaces and lockfiles.
- The npm manifests and lockfiles in `ui` and `extension`.
- The Debian base image in `dist/docker/Dockerfile`.

Cargo and npm minor/patch updates and major updates use separate groups across their directories.
Each ecosystem permits two open version-update PRs, so a major group can be reviewed alongside
the minor/patch group. Weekly checks are staggered in Australia/Sydney time: Cargo at 02:00, npm
at 04:00, Actions at 06:00 and Docker at 08:00. A release is proposed only once it is 3 days old
(`cooldown`, Dependabot's default written down; zizmor is configured to accept it): a hijacked
release is usually pulled within days. Security updates use separate groups when enabled in
repository settings and remain driven by alerts; the schedule, the cooldown and the limit do not
delay them. Path selection runs the CI jobs a change needs. Updates still require successful
checks before merging.

When updating `@playwright/test`, update the Playwright container tag and digest in `ci.yml`
in the same PR. `extension/test/ci.test.ts` rejects a mismatch. Dependabot's npm update may
need that companion image change before it passes CI.

The `Review dependency changes` job in `ci.yml` (PRs that change a manifest, a lockfile or a
workflow) fails when a dependency change introduces a known high or critical vulnerability,
including development dependencies. Its report goes
to the job summary without requiring PR-comment write permissions. This checks the PR's
dependency delta; Dependabot alerts and `cargo deny` cover existing vulnerable dependencies.
License enforcement remains in `cargo deny`.

## Repository settings

Workflow files and `dependabot.yml` cannot enable repository-level security settings. An
administrator should verify these under **Settings → Security → Advanced Security** (called
**Code security and analysis** in some GitHub interfaces):

1. Enable the dependency graph, Dependabot alerts and Dependabot security updates. The graph
   also supplies the dependency review check. Dependabot version updates activate when this
   configuration is merged into the default branch.
2. Use CodeQL **advanced setup** with `ci.yml`. If default setup is already enabled, disable
   it to avoid conflicting analysis uploads. The Actions configuration that `codeql.yml` used to
   upload (`/language:actions`) is no longer uploaded; delete it under **Security → Code
   scanning → Tool status** if GitHub reports it as stale.
3. Require the `CI` check in the `main` branch protection or ruleset. It covers every job a PR
   runs (dependency review included) and passes only if change selection succeeded and each
   selected job passed; unselected jobs skip. CodeQL doesn't analyze PRs: it detects problems
   after merging, on `main` and weekly, and its alerts are reported separately. Don't add a
   code-scanning merge-protection rule for CodeQL: PRs have no CodeQL results for it to check.
   Restore PR analysis first if merges must wait on CodeQL alerts.

These features are available for this public GitHub repository. A move to a private repository
may require GitHub Code Security for code scanning and dependency review.
